# ADR-0056: The API contract is checked against the server's traffic

- **Status:** Accepted
- **Date:** 2026-11-01
- **Deciders:** @tapionx
- **Related:** ADR-0016, ADR-0024, ADR-0050, API-001, API-002, API-007

## Context

API-002 asked CI to compare the OpenAPI document generated by the server with
the committed contract. The two are written differently: the contract by
hand, with its own schema names, descriptions and ways of expressing
nullable fields; the generated one by FastAPI from the server's models. A
textual comparison fails on form alone, and making the two identical would
make the contract follow the code, when the contract is the source of truth.
What clients rely on is what the server accepts and sends.

## Decision

1. **Operations match.** A design test lists the server's routes, as method
   and path template, and the contract's operations. They must be the same:
   the server serves nothing the contract does not describe, which is also
   API-001's "no private endpoints", and nothing in the contract is missing.
2. **Traffic matches.** The test harness's HTTP client checks every exchange
   with the server against the contract:
   - the response's status must be one the operation lists, and its body,
     when it has one, must match the schema of that status and content type;
   - each event of an event stream must match the contract's event schema;
   - a request the server accepted, with a `2xx` status, must match the
     operation's request body schema, so that the server never accepts what
     the contract forbids.

   Schemas are checked as JSON Schema 2020-12, which OpenAPI 3.1 uses, with
   the formats `uuid`, `date-time` and `uri` checked. A mismatch fails the
   test that caused it.
3. **Error codes are documented.** A design test collects every error code
   the server's code can produce, in problem responses and in `RUN_ERROR`
   events, and checks that each is in the contract's `ErrorCode` (API-007).
4. **Mismatches are fixed in the server,** unless the contract is wrong; then
   the contract changes first, in a `spec/` pull request.

## Consequences

- The contract is checked only where the tests exercise the API, so a status
  or field that no test reaches is not checked. Test coverage of the API
  becomes coverage of the contract.
- The contract must list every status an operation can return, including
  `422` for invalid bodies and the problems shared by all operations.
- The server keeps not serving a generated document; clients use the
  committed one.

## Alternatives considered

- **Compare the generated document with the committed one:** fails on
  presentation, and pushes the contract to follow the code.
- **Generate the contract from the code:** the contract would no longer be
  written before the code, which the project's workflow requires.
- **Property-based testing from the contract (e.g. Schemathesis):** finds more
  edge cases, but adds a tool and a long-running job; it can come later on top
  of this check.
