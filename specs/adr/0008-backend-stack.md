# ADR-0008: Python backend with FastAPI, Pydantic AI and PostgreSQL

- **Status:** Accepted
- **Date:** 2026-10-29
- **Deciders:** @tapionx
- **Related:** ADR-0009, ADR-0016, ADR-0017, API-001, API-004

## Context

The backend orchestrates everything: authentication, conversations, the
agent loop, tools, memory, scheduling, sandboxes and model calls. Its work is
mostly I/O-bound and long-running (streaming model output, waiting for
sandboxes). The maintainer reviews Python more comfortably than other
languages, and the Python ecosystem for LLM agents is the richest.

## Decision

We will build the backend with:

| Concern | Choice |
|---|---|
| Language and tooling | Python 3.13+, `uv`, `ruff`, `pyright` in strict mode |
| HTTP framework | FastAPI on an ASGI server |
| Schemas and validation | Pydantic v2 |
| Database | PostgreSQL (row-level security, JSON, full-text search, pgvector) |
| Data access | SQLAlchemy 2 (async) with asyncpg; Alembic migrations |
| Background jobs and schedules | procrastinate (PostgreSQL-backed, no Redis) |
| Agent loop and tools | Pydantic AI |
| Tool protocol | MCP, via the official Python SDK |
| Model access | A model gateway (ADR-0017), LiteLLM as the initial candidate |
| Streaming to clients | Server-Sent Events |
| Sandbox driver client | Async Docker API client (aiodocker), Kubernetes later |
| Tests | pytest, httpx, testcontainers |

Rules that follow from this choice:

- The backend is fully async; blocking calls never run on the event loop.
- Type checking is strict; untyped code does not pass CI.
- The OpenAPI document generated by FastAPI is checked against the committed
  contract (API-002), and client code (TypeScript, Dart) is generated from
  the contract, recovering type safety across the API boundary.
- The web client is written in TypeScript; its framework is decided in a
  later ADR.
- Speech-to-text and text-to-speech run as separate services behind an
  OpenAI-compatible audio API, not inside the backend process.

## Consequences

- One language for the whole server side, with the best agent ecosystem.
- No types shared natively with the web client; mitigated by generated clients.
- Async discipline must be enforced by review and design tests.

## Alternatives considered

- **TypeScript (Node.js) with Fastify, Zod, Drizzle and pg-boss:** shared
  types with the web client and a strong agent SDK ecosystem; rejected in
  favor of the maintainer's stronger familiarity with Python.
- **Go or Rust:** excellent for the sandbox driver and single binaries, but a
  thinner agent ecosystem and more code for the same features.
- **Prisma or ORMs that make row-level security awkward:** rejected because
  tenant isolation depends on transaction-scoped database settings (ADR-0009).
